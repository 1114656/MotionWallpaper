# 视频运行环境与验证范围

更新日期：2026-09-23。

本页区分程序当前检查的条件、建议覆盖的测试环境，以及尚未认证的组合。项目没有根据显卡名称强制要求“RTX 2060 以上”，也不能根据显存大小推断某个视频一定可以硬解或硬编。

## 基本运行条件

- x64 Windows，发布最低基线为 Windows 10 22H2 / build 19045，或 Windows 11。这个最低目标不等于已经完成所有 Windows 10/11 版本的实机测试。
- Windows Media Foundation 能播放生成的 H.264 输出。Windows N 须先在系统“可选功能”安装 Media Feature Pack 并重启；安装器会检查媒体组件文件是否存在。0.2.1 的原画模式遇到系统缺少解码器时，可以尝试随包 HEVC/H.264 解码器；仍需所选显卡和驱动支持具体 profile，或输入符合 CPU 兼容预算。
- 使用程序随包提供、版本固定的 FFmpeg、ffprobe、相应 DLL 与 OpenH264 依赖；只替换一个 `ffmpeg.exe` 不能保证包内 API、滤镜、编码器和依赖仍然匹配。
- 为源文件、临时输出和已完成副本保留足够磁盘空间。程序不通过覆写原视频来节省转码空间。
- 单目录存储要求当前用户能写入程序目录中的配置、日志及默认媒体库；安装与启动阶段会检查目录权限。不要依靠长期以管理员身份运行来绕过只读目录。

输入文件可由 FFmpeg 探测和转码，不要求本机先具备该源格式的系统解码器；完整输出仍必须通过本机 Media Foundation 首帧检查。扩展名 MOV/MP4 不能代替输入能力判断。

## 档位目标与兼容预算

平衡档按显示器物理分辨率匹配，帧率目标为 `min(源帧率, 显示器 Hz)`：源帧率足够时，2K60 显示器目标为 2K60，1080p60 显示器目标为 1080p60。节能档最高 1080p，使用相同的帧率上限，144 Hz 屏可以对应 1080p144。低规格源不放大、不插帧；高刷节能不保证始终达到最低功耗。

这些是档位目标，不是所有 GPU 都支持 2K60 或更高规格的承诺。内部 CPU 兼容预算仍最高 1080p60 或更低；它不修改用户档位定义。只有不改变所选输出目标且满足安全预算时才可更换编码后端，否则必须报告不可用和详情，不能静默降档。

原画失败时保留源文件和失败详情，提示用户生成平衡或节能副本；点击后才进行转码及应用。用户未发起转换时，不把后台生成或使用兼容副本当成原画成功。

## NVIDIA 驱动与工具链

当前随包 FFmpeg 的 NVENC 路线使用要求 NVIDIA Video Codec SDK 13.0 API 的工具链。该 SDK 的 Windows 驱动基线为 **570 或更高**；这限制的是当前 NVENC 路线，不是所有历史版本 FFmpeg 或程序全部功能的永久门槛。[NVIDIA SDK 13.0 官方要求](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/read-me/index.html)

早期故障记录使用 GTX 1070、驱动 560.94；2026-09-23 的提速实测已更新到驱动 582.66。该组合此前实际报告“要求 NVENC API 13.0、驱动提供 12.2”，但已经观察到旧管线通过 GPU 解码辅助 OpenH264 CPU 编码完成一个完整视频。这个事实说明编码与解码能力必须分开，不能据此宣称 v6 全部素材或该型号全部驱动已经认证。

对不满足当前 NVENC API 的驱动，程序应跳过确定不兼容的硬件编码候选，并在失败详情中明确驱动要求。若所选输出目标仍在 CPU 安全预算内，可以尝试保持该目标的 CPU 编码，输入硬解有效时可由 GPU 辅助解码；例如要求 2K60 而又没有合格硬编路线时，应明确失败，不能偷偷生成 1080p60 后声称达到平衡目标。软件转换长视频可能耗时数分钟，预检通过也不会使完整编码变成即时操作。

更新到满足 API 要求的驱动后，仍需具体显卡支持相应输入解码和 H.264 编码，且短片段输出通过验收。版本号达标不是所有视频都会成功的充分条件。

## Intel、AMD 与混合显卡

Intel Quick Sync、AMD AMF 候选已进入探测、短片段预检和输出验收流程，但目前没有完成 Intel / AMD / NVIDIA 三厂商、多个代际及驱动版本的完整实机认证。

多显卡机器按具体 DXGI 适配器和 LUID 选择路线。厂商相同、显存较多或被设为高性能 GPU，都不能证明支持 HEVC Main10、AV1 或某个目标编码参数。输入硬解与输出硬编应分别观察；后台任务最终使用的路线以日志和实际结果为准。

显式软件解码不向 Media Engine 提供 DXGI manager，CPU 输出通过 WIC BGRA 上传到优先选择的物理 GPU 呈现；物理设备创建失败后才回退 WARP。CPU 解码与呈现设备选择已分离，但软件缩放和视频处理仍可能在 CPU 执行，不属于全程 GPU 路线。[Media Engine DXGI manager 官方说明](https://learn.microsoft.com/en-us/windows/win32/medfound/mf-media-engine-dxgi-manager)

同一显卡、同一视频、同步播放的输出可以共享解码；每块屏幕按自己的刷新节奏呈现，刷新率不同不再单独阻止共享。

## 随包原画解码（0.2.1）

Windows 播放路径首次出现 `MF_E_TOPO_CODEC_NOT_FOUND` 时，Renderer 在同一进程内动态加载固定版本 FFmpeg，不安装或注册系统解码器。优先复用已有 D3D11 设备进行硬解，NV12/P010 画面保持在 GPU，色彩转换和各屏裁切由 shader 完成；软件兼容输入限制为不超过 1080p 像素量、60 FPS，不能通过降低原片分辨率冒充原画。已有 Windows H.264 路径不依赖备用库。

一条播放路线只有一个解码器、一个时钟，待呈现帧队列最多 3 帧。源帧率超过目标显示帧率两倍时，解码器允许跳过非参考帧，保留解码依赖；仍需解码的参考帧无法任意跳过。若设备持续追不上原片，必须报告性能不足并建议生成副本，而非无限忙转或无提示地停在首帧。

当前桌面输出是 sRGB SDR：支持常见 SDR、P3、PQ/HLG 的显示转换，HDR 不做 HDR 直通。MOV 明确的容器色彩标签优先于内部通用标签，与性能副本及高清静态图保持一致。Dolby Vision、无法识别的矩阵/色彩、镜像或透视显示矩阵会明确失败；不能把这些输入列为已支持。PQ 读取亮度元数据，缺失时使用 1000 nit 假定，HLG 使用 1000 nit 显示参考。详细验证与边界见 [0.2.1 本地验证](RELEASE_0.2.1_LOCAL_VALIDATION.md)。

## 建议的实机验证基线

下面是待覆盖的验证组合，不是宣称已通过的支持清单，也不是程序硬编码的最低显卡型号。

| 组合 | 主要目的 | 需要记录 |
| --- | --- | --- |
| GTX 1070 / 560.94 历史故障环境 | 明确 NVENC 驱动不兼容；验证预算内 CPU 路线与超预算失败提示 | 所选目标未被暗改、错误详情、尝试次数、CPU/GPU 使用 |
| 支持 H.264 NVENC 且驱动满足当前 API 的 NVIDIA 环境 | 硬编成功路线与驱动升级后的能力重检 | GPU 型号、驱动、FFmpeg 版本、预检和完整输出 |
| 具有 Quick Sync 的 Intel 核显环境 | 核显硬解/硬编及资源预算 | CPU/核显代际、驱动、插电/电池状态 |
| 支持 AMF H.264 的 AMD 环境 | AMD 参数兼容与输出验收 | GPU 型号、驱动、硬编失败时回退结果 |
| 核显加独显、同厂商双卡 | 适配器绑定、输入解码与输出编码的选择 | 具体 LUID、实际路线、两屏播放状态 |
| 软件回退环境 | 无可用硬编时仍能生成可播放 SDR 文件 | 线程/尺寸预算、长时负载、输出播放检查 |
| Windows 10 与 Windows 11 各一台 | 检查当前兼容目标和系统媒体栈差异 | 完整系统版本、媒体组件、首帧与循环行为 |

每种环境至少覆盖 H.264 SDR、HEVC Main10 SDR、PQ、HLG、非 MF 原生输入、240/239.76 FPS、低帧率有理数输入、损坏/异常色彩文件，以及双屏不同刷新率。档位验收至少包含 60 Hz 屏平衡 2K60/1080p60、144 Hz 屏平衡 144 FPS 与节能 144 FPS、源帧率不足时不补帧，以及节能 1080p 尺寸上限和低规格源不放大。还应检查原画失败未点击时不自动转码、点击生成后的实际应用，以及转码期间屏保、锁屏、熄屏、电池切换、暂停、取消和退出，记录源文件 SHA-256 是否保持不变。

## 自动化与支持承诺

从仓库根目录执行：

```powershell
.\scripts\build-native.ps1 -SkipPublish
.\scripts\test-video-pipeline.ps1
```

`-SkipPublish` 仍准备测试依赖 FFmpeg / ffprobe；首次运行可能下载固定版本工具。视频回归脚本有进程超时，生成 SDR、PQ、HLG 10-bit MOV 及 90° 容器旋转 MOV，并检查输出规格、完整解码、源文件哈希及亮度异常。结果保存为独立目录内的 `summary.json` 和逐步日志。

自动化通过表示这些具体输入和检查通过。它不证明 HDR 色调映射已经过视觉认证，也不证明某个硬件编码器实际被采用；需要结合候选日志确认是否回退到 CPU。

当前接通电源时允许副本任务跨屏保、锁屏和熄屏继续，安全锁和睡眠规则照常生效。电池供电、用户停止或进程退出仍会丢弃本次部分编码，后续从头生成；界面使用“停止 / 重新生成”明确这一行为，尚未实现跨进程断点续编码。

生成阶段默认优先完成：FFmpeg 使用普通进程与内存优先级，显式关闭执行速度 EcoQoS，滤镜线程随 CPU 配置增加、最高 12 个，解码缓冲和 CPU 编码线程仍有边界。8-bit、BT.709、有限范围、无需旋转或裁切的输入可以在同一 GPU 内解码、缩放、编码；NVIDIA CUDA 设备按 LUID 匹配，不使用 DXGI 序号猜测。该路线预检失败仍尝试兼容路线。P3、HDR、10-bit 及色彩信息不足的输入保留明确的色彩转换和抖动；没有承诺所有素材都能全程 GPU 处理。播放阶段的分辨率、帧率与省电策略独立保留。
