# 自适应视频画质（开发版）

此规则更新平衡档，不改写原文件；任务页提供针对单个视频的兼容生成入口。安装包的历史发布记录不代表本次新增路径已经完成硬件矩阵认证。

| 档位 | 尺寸与帧率 | 编码、精度和色彩 |
| --- | --- | --- |
| 原画 | 直接使用源视频 | 不转码；实际呈现按显示能力转换，播放失败明确报告 |
| 平衡 | 按所选显示器的物理尺寸与刷新率，受源规格上限约束 | 源 ≥10-bit 时先试 HEVC Main10 硬编与实际硬解；不通过则回退 H.264 8-bit。源 8-bit 不升为 10-bit |
| 节能 | 最高 1080p（竖屏对应旋转尺寸），帧率不超过源视频和屏幕刷新率 | 固定 H.264、8-bit、BT.709 SDR；降位深使用抖动，HDR 使用线性光色调映射 |

所有档位不插帧。平衡和节能不放大小尺寸原片。原画使用源文件不等于有损编码变成无损，也不等于屏幕支持原片的所有色彩。

## 独立的色彩能力

- 10-bit 是副本编码/解码精度，和显示器是否支持 HDR 分开判断。SDR 屏幕也可以使用 10-bit SDR 副本，最终显示精度受屏幕输出限制。
- 源已经是 BT.709 色域时，支持的 SDR 曲线（BT.709、sRGB、gamma 2.2、BT.2020 SDR）可独立于高级颜色开关保留。8-bit 的非 BT.709 曲线也使用内置解码/色彩 shader，避免交给未经验证的系统颜色解释。
- `DisplayConfigGetDeviceInfo` 查询 Windows 是否已启用高级颜色；`IDXGIOutput6::GetDesc1` 的当前 PQ 色彩空间确认 HDR 已开启。检测失败按 SDR 处理。
- 高级颜色可用时，已知的 P3/BT.2020 色域可以保留。PQ/HLG 仅在源本身为 HDR、10-bit 路径可用且显示器 HDR 已开启时保留；否则做 HDR→SDR 转换。WCG SDR 屏可保留广色域 SDR，与是否保留 HDR 分开。
- Renderer 高色彩路径使用内置解码器，逐屏选择 BGRA8 SDR 或 FP16 scRGB。scRGB 保留负值和超过 1 的颜色分量，按 Windows SDR 白电平缩放 SDR；PQ 的绝对亮度按 scRGB 的 80 nit 参考白换算。HDR 在 SDR 输出上做色调映射。
- `CheckColorSpaceSupport` / `SetColorSpace1` 或 FP16 交换链创建失败时，输出转为 SDR 并记录日志。原文件不改，缓存仍保留原有色彩信息。
- HDR 重编码不携带旧 Dolby Vision 动态指令；只有不改变 HDR 传递函数的路径才允许保留静态 HDR 帧元数据。Dolby Vision 直通不在支持范围。

## 生成与缓存

先编码两秒样片，检查尺寸、帧率、像素格式、位深和色彩标记。Main10、广色域和非标准 SDR 曲线还通过独立 Renderer 子进程验证实际硬件解码与 SDR/FP16 shader 绘制；不依赖 Windows HEVC 商店扩展。预检不是长时间流畅度或真实显示器颜色认证，无法自动识别所有视觉偏色。

优先依次尝试可用硬件编码器的 Main10 路径，全部失败后才尝试 8-bit。软件编码保持现有尺寸、帧率及线程预算；不会为了保留 10-bit 无限制进行 CPU 重编码。色彩、位深、范围和画幅完全一致的 SDR 输入可用 GPU 缩放，否则使用明确的色彩转换路径。

自动颜色路径的 10-bit/8-bit 均不可用时，改试 CPU 颜色转换的 BT.709 SDR 兼容路径，并重新按源精度尝试 10-bit、8-bit。GPU 缩放失败时仍可用 CPU 滤镜和硬件编码。每次预检与最终产物都先核对本次实际尝试的严格颜色契约，不能因为允许兼容回退而接受标签错误的输出。

NVIDIA CUDA 缩放使用固定内核 `use_filters=0` 并保留 `passthrough=0` 的独立帧池。在本机 GTX 1070/P010 上，当前 FFmpeg 的自动滤镜方式曾输出黑帧；不能靠重写色彩标签掩盖此问题。GPU 路径仅对不需要颜色变换的输入使用，并给滤镜输出明确设置已经验证的同一颜色属性，避免编码器改写传递函数。

任务页的“颜色异常？兼容生成”仅影响所选视频的平衡副本：强制 CPU 颜色处理到 BT.709 SDR，解码/编码仍优先用硬件，源 10-bit 在通过验证时保留；节能及原画不受影响。“恢复自动生成”撤销该偏好。生成任务进行中或源文件缺失时不可切换。请求用独占文件句柄协调偏好与新任务 GUID，旧请求不能发布到新偏好下。

平衡缓存使用 `balanced-…-adaptive-sdr|wide|hdr-v8.mp4`；8-bit 回退也属于对应自适应请求，实际格式以文件探测为准。旧 v7 平衡副本不会冒充新策略结果。节能和内部 CPU 兼容副本继续使用 v7 的固定 SDR 契约。多屏色彩能力不同会分别选择副本；同一 GPU、同一实际文件、同步播放仍可共享解码。

手动兼容副本独立使用 `balanced-…-compatible-v9.mp4`，不会误用保留原颜色的自动副本。旧 v8 中通过格式、时长和实际播放验证的标准 BT.709 SDR 副本继续复用，不因这次提速更新强制重建。源 8-bit 不接受 10-bit 副本。

## 山谷示例

实测原片：3840×2160、240 FPS、HEVC Main10、10-bit、P3 D65、gamma 2.2，属于 **SDR**。

- 4K 60 Hz 普通 SDR 屏：优先生成 4K60 HEVC Main10、10-bit BT.709 SDR。
- 4K 60 Hz 且 Windows 高级颜色可用：优先生成 4K60 HEVC Main10、10-bit P3 SDR；不会凭空生成 HDR。
- Main10 编码或硬解预检失败：回退同尺寸、帧率的 H.264 8-bit，色域继续按显示能力决定。
- 节能：最高 1080p60 H.264、8-bit BT.709 SDR。

## 验证边界

自动化覆盖精度不升级、独立 HDR/色域回退、色彩缓存分离、P3 负值/超范围色彩、HDR 高光及 SDR 白电平的真实像素读回，以及已有暂停/恢复、共享呈现、缓存原子发布等回归。实际 HDR 面板观感、Intel/AMD、多 GPU 混合 HDR/SDR 长时播放仍需实机验收。

### 本地验证（2026-09-28）

- 发布构建成功，125 项原生回归测试通过，开发版已更新并启动。
- GTX 1070 上使用“山谷”原片的 4 秒片段，验证 4K60 Main10 P3 SDR、4K60 Main10 BT.709 SDR，以及 1080p60 H.264 8-bit SDR。输出均通过格式检查和完整片段解码；Main10 通过内置硬解预检。
- 人为拒绝 Main10 预检后，成功回退 H.264 8-bit。后台优化队列实际完成生成、发布与采用，重复请求命中缓存；原画仍返回源文件。
- 合成 PQ 和 HLG 样片验证 HDR 保留与 SDR 转换；FP16 像素读回验证广色域和 HDR 高光没有提前裁剪。“山谷”完整原文件 SHA-256 保持不变。
- 当前检测输出为 4K60 SDR，未启用 Windows 高级颜色；上述结果不代表真实 HDR 面板或其他厂商显卡已验证，也不代表已经转完整段“山谷”视频。

### 本地验证（2026-09-29）

- 发布构建成功，131 项原生回归测试通过，现有开发目录已更新并重新启动，保留配置与媒体库。
- GTX 1070 上用“夕阳”的约 12 秒片段比较 4K60 Main10 生成：自动 GPU 缩放 24.287 秒，CPU 兼容颜色转换 36.719 秒，均包含两秒样片预检等启动开销，单次样本耗时减少约 34%。该短测不能直接预测完整视频的剩余时间。
- 自动副本保留源 BT.709 色域、sRGB 曲线和 10-bit；兼容副本转换到 BT.709 曲线并保留 10-bit。两个输出均完成全片段解码与非黑画面抽样检查。
- 独立测试媒体库完成“自动生成 → 手动兼容生成 → 恢复自动”的生成、发布、采用与缓存复用，原画模式仍返回原文件。人为拒绝自动颜色样片的测试也成功进入 CPU 兼容颜色路径，并保留 Main10。
- 实测修复当前 FFmpeg CUDA 自动滤镜在本机 P010 路径产生黑帧的问题，固定内核的原尺寸 4K 及缩放 1080p 样片均通过验证。此结果尚未覆盖其他厂商、驱动及真实 HDR 显示器。
