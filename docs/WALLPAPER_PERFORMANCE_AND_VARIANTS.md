# 壁纸性能档位与优化副本设计

更新日期：2026-09-23。当前档位规则为：平衡使用显示器分辨率与刷新率，节能最高 1080p 且跟随显示器刷新率，两者均不超过源帧率。此前平衡“刷新率加 30”的方案已被替代。历史验证报告保留执行时的真实输入与结果，不代表最终档位规则已经按全部环境复验。

## 产品目标与边界

优先保证稳定播放和日常省电，允许性能副本降低分辨率、帧率及位深，并把支持的 HDR 输入转换为 SDR。转换始终另写文件，不修改导入源文件。“原画直出”仍直接读取源文件；用户主动删除源文件是独立的媒体管理操作。

`.mov` 是容器名，不是编码或性能等级。输入信息需要包含视频编码、profile、像素格式、位深、色度采样、色彩标记、尺寸、帧率和时长。能读取输入、能硬解输入、能硬编输出、Windows 能播放输出是分别检查的能力。

当前 Renderer 使用 8-bit BGRA 交换链。保留源文件或直接播放源文件不等于已经实现端到端原生 HDR 呈现，也不保证每个源格式都能由本机 Media Foundation 播放。

## 输出档位

| 档位 | 视频选择 | 尺寸上限 | 帧率上限 | 色彩与编码 |
| --- | --- | --- | --- | --- |
| 原画直出 `original` | 直接读取源文件 | 源尺寸 | 源帧率 | 不重编码；受本机源格式播放能力限制 |
| 自动平衡 `balanced` | 源已符合目标时可复用，否则生成副本 | 按当前显示器物理分辨率匹配，保持宽高比且不超过源规格 | `min(源帧率, 显示器刷新率)` | MP4 / H.264 / 8-bit 4:2:0 / BT.709 SDR / 有限范围 |
| 低功耗 `power-saver` | 源已符合目标时可复用，否则生成副本 | 横向最高 1920×1080，竖向对应 1080×1920；不超过源规格或实际显示需求 | `min(源帧率, 显示器刷新率)`，不固定为 60 FPS | 与自动平衡相同 |
| 内部兼容副本 `cpu-smooth` | 软件播放或自动解码回退所需的兼容文件 | 按当前 CPU/显示器预算，最高 1080p | 最高 60 FPS，较低性能预算可降至 30 FPS | 与自动平衡相同 |

`cpu-smooth` 不是第四个用户档位。其最高 1080p60 或更低的 CPU 安全预算，不是平衡或节能档的帧率上限，也不能作为原画失败后静默转码的理由。自动模式会对实际选中的文件重新探测硬解能力：不能硬解 HEVC 源视频，不等于不能硬解生成后的 H.264。更换编码后端不应改变用户选择的输出目标；目标超过安全预算或无法播放时，明确报告失败，不能把较低规格显示成所选档位已经应用。

尺寸保持源宽高比，不放大低分辨率源文件，最终显示时由 Renderer 缩放和裁剪。平衡档按显示器物理像素需求选型，与 Windows 的界面缩放比例无关；高分辨率、高帧率输出必须受源规格和实际硬件能力约束。节能档固定的是最高 1080p 的尺寸预算，不是固定帧率；高刷新率下它不一定是功耗最低的选择。

源帧率不高于档位上限时，编码参数保留源有理数帧率，例如 `24000/1001`、`30000/1001`，不为了凑整到 24/30/60 而补帧；高于上限时才降帧。对可变帧率或异常时间戳的素材仍需实测，不能把平均帧率相等视作时间轴完全不变的证明。

| 源素材 | 当前显示器 | 自动平衡示例 | 低功耗示例 |
| --- | --- | --- | --- |
| 3840×2160，240 FPS | 2560×1440，60 Hz | 2560×1440，60 FPS | 1920×1080，60 FPS |
| 3840×2160，240 FPS | 1920×1080，60 Hz | 1920×1080，60 FPS | 1920×1080，60 FPS |
| 3840×2160，240 FPS | 2560×1440，144 Hz | 2560×1440，144 FPS | 1920×1080，144 FPS |
| 3840×2160，60 FPS | 2560×1440，144 Hz | 2560×1440，60 FPS | 1920×1080，60 FPS |
| 3840×2160，24000/1001 FPS | 2560×1440，60 Hz | 2560×1440，24000/1001 FPS | 1920×1080，24000/1001 FPS |
| 1280×720，30000/1001 FPS | 2560×1440，144 Hz | 1280×720，30000/1001 FPS | 1280×720，30000/1001 FPS |

帧率、尺寸相同不代表可以跳过转换：编码、位深和色彩也必须满足目标。例如 1080p30 HEVC Main10 仍可能需要转成 H.264 SDR。

表中是期望输出规格，不是所有 GPU 的兼容承诺。尤其是 4K60、2K144 等规格，必须通过候选预检和实际播放验收；不能以受限 CPU 回退悄悄把目标降为 1080p60 后报告成功。

## 原画失败后的用户操作

原画直接读取并保留源文件，不因源解码失败而自动生成或应用其它档位。失败状态应显示可理解的原因，提供“查看详情”“生成平衡副本”和“生成节能副本”。用户点击一个生成操作后，才按该档位创建请求、转码并在验收成功后应用；未点击时继续保留失败状态与源文件。

生成失败应保留源文件、当前目标和失败详情，包括必要的编码器/驱动错误；不能静默切换用户档位或用兼容文件冒充原画。任务取消、暂停与电池规则在用户发起转换之后照常生效。

## HDR、色域和位深

所有新生成的 v7 性能副本遵循同一输出合同，不由“选中了哪个编码器”决定画质政策。

- 普通 SDR 高位深输入转换为 8-bit SDR，保持明确的 BT.709 输出标记。
- PQ、HLG 输入先按输入传递函数线性化，执行实际亮度映射与色域转换，再编码为 BT.709 SDR。
- BT.2020 等广色域输入需要色域转换；仅把标签改成 BT.709，或仅执行 `format=yuv420p`，不构成正确的 HDR→SDR 转换。
- 输出必须同时满足编码、像素格式、色彩原色、传递函数、矩阵和范围的目标检查。色彩未知、矛盾或不支持的组合不能冒充已验证成功的 SDR 副本。
- 转码文件是有损性能副本，不承诺视觉上等同 HDR 原片。自动化标签和亮度检查不能代替参考显示器上的视觉色彩验收。

原文件保留原始字节和色彩元数据；性能副本的色彩不再要求与原文件标签相等。

## 输入、预检和完整输出验收

1. **保存输入。** 导入先保留源文件，检查文件和资源上限。随包 ffprobe 读取结构化媒体信息，不再以系统 Media Foundation 是否认识源格式作为唯一导入门槛。
2. **生成封面。** FFmpeg 在独立、有超时的进程中提取 480×270 范围内的列表封面。桌面等待性能副本或原画播放失败时，Agent 另行按需提取最高 4K 的静态帧，完成后自动替换小封面。仅解码一帧，提取失败保留小封面；没有任何可用封面时等待副本，不启动持续播放的源解码器。高清图写入 `Config/DesktopPreviews`，缓存清理目标为 128 MB，正在显示的图片受租约保护，可暂时超额；列表不加载高清缓存。
3. **生成预检片段。** 对每个候选路线先转换约 2 秒视频，单次预检编码的墙钟上限为 45 秒。这是候选预检上限，不是完整长视频的总转码上限。
4. **验收候选。** 检查片段输出规格，并通过独立子进程调用 Media Foundation 实际解出首帧；首帧探针最多等待 10 秒。超时或失败可以终止该探针并尝试下一条路线，不在 Agent 线程内无限等待系统解码器。
5. **转换完整视频。** 通过预检的候选执行完整编码，继续报告进度、处理取消并监测停滞。
6. **完整验收与发布。** 完整文件仍需检查编码、像素格式、尺寸、帧率、时长、色彩元数据及实际首帧。验收通过后才原子发布到正式副本路径；短片段成功不能跳过整片验收。

输入探测和输出探针均有超时/取消边界，但没有为任意视频长度设定同一“几秒内完成”的承诺。

## 编码与解码路线

候选按具体 DXGI 适配器选择并绑定 LUID，分别尝试 NVIDIA NVENC、Intel Quick Sync、AMD AMF 和受限的 OpenH264 软件编码。编码器被 FFmpeg 编译进去，不代表当前显卡、驱动和参数可用；以预检和输出验收结果为准。

GPU 解码与 GPU 编码是独立能力。旧驱动导致 NVENC 不可用时，只有 CPU 编码可以在安全预算内满足所选目标，才可保留同一目标尝试该后端；输入仍可硬解时可以采用 GPU 解码辅助 CPU 编码。目标超出预算或所有候选失败时，必须展示失败及驱动/编码器详情，不能暗中降分辨率或帧率。确定的驱动 API 不兼容应快速跳过，不能反复尝试同一不支持的组合。

当前链路并非全程 GPU：部分路线仍下载帧到 CPU 做缩放、色彩处理，再交给编码器。纯 GPU 缩放和完整厂商特定滤镜路线不是本次已完成能力。显式软件播放不向 Media Engine 提供 DXGI manager，CPU 输出经 WIC BGRA 上传到物理 GPU 呈现，物理设备创建失败后才回退 WARP；软件缩放和视频处理仍可能在 CPU 执行。

运行环境及驱动说明见 [视频运行环境](VIDEO_ENVIRONMENT.md)。当前没有硬编码“必须 RTX 2060 以上”之类的显卡型号门槛。

## 任务生命周期与电源

任务调度与桌面呈现分别处理：

| 事件 | 呈现行为 | 副本生成行为 |
| --- | --- | --- |
| 桌面进入屏保，接通电源 | 有副本则播放；缺副本时显示可用海报 | 所有档位继续已有生成任务 |
| 锁屏或显示器熄灭，接通电源 | 停止 Renderer，不把窗口放到安全桌面 | Renderer 停止后允许继续生成 |
| 解锁或唤醒显示器 | 恢复符合当前档位的画面 | 不因海报 ACK 尚未到达而丢弃已有安全任务 |
| 转为电池供电 | 用户选择的档位保持不变 | 停止本次编码，持久请求等待接通电源 |
| 用户暂停生成 | 保留合适的可显示状态 | 停止本次编码，保留请求；继续时从头生成 |
| 用户取消生成 | 已完成副本不受影响 | 删除请求和本次临时输出 |
| 进程退出或系统重启 | 正常退出播放 | 当前部分编码不能跨进程续接；后续重新生成 |

继续后台生成不阻止 Windows 自动锁屏、熄屏或睡眠，不修改用户安全设置。**目前没有可恢复的分段编码或跨进程断点续编码。** “保留任务请求”只表示之后可以重新排队，不表示恢复到之前的百分比。电池、暂停或退出后不得将旧百分比显示成当前编码已经完成的部分。

等待副本时不回退播放高负载原视频来绕过所选档位。存在海报时使用海报；没有海报时停止对应视频路线，允许系统桌面背景暂时可见，并报告等待/生成状态。已没有 Renderer 的停止或暂停状态直接视为停止/暂停，不显示虚假的 `pause-pending`。

## 缓存、并发和发布

- 每个媒体目录下使用独立的 `Variants` 存储派生文件。v7 文件名包含档位、目标帧率、目标尺寸和策略版本，`cpu-smooth` 仍有独立前缀。
- 相同参数的请求合并；显式请求采用 `mode|requestId` 标识。新请求、完成、失败和清理都核对请求所有权，旧工作线程不能删除新请求的状态。
- 同一档位允许保留多个已经完成的 v6/v7 规格，避免每次显示拓扑切换都删除旧规格再重转。旧策略版本按迁移与清理规则处理，不能仅因扩展名相同就认作当前策略文件。
- 总缓存配额与近似 LRU 决定淘汰。使用时间有节流更新，当前 Renderer 的播放租约、正在发布的输出及必要的可播放文件受到保护；配额不意味着强制删除正在使用的文件。
- 自动平衡和低功耗在规格等价时可以共享物理文件，容量统计按物理占用去重。
- 临时输出使用独立 token，不可被当作完成的副本选择。验收后原子替换正式文件；外置媒体库继续使用稳定卷身份和受保护的操作范围。
- 首次采用已有副本时检查 SDR 规格、完整时长和 Windows 首帧，按文件身份、大小、修改时间及目标规格缓存结果。损坏文件被有效文件替换后重新验收，不继续复用旧失败结果。
- 磁盘预留使用当前编码策略的最大输出大小加 256 MB，而不是源文件大小的固定倍数。
- 缓存命中不应每次策略轮询都写日志。日志轮转必须在关闭读取句柄之后替换文件，并协调多个写入者。

源文件删除、媒体库备份、迁移和回收站属于独立用户操作。删除源文件至少应保留一个可播放副本；源文件不存在后，原画模式和重新生成副本不可用。

## 多显示器与状态交接

同一源媒体聚合目标显示器的物理分辨率和刷新率需求，再按所选档位与源规格约束选型。例如 2K60 与 1080p60 显示器播放同一 4K240 源时，平衡档可以共用 2K60 副本，1080p 屏独立缩小；节能档可共用 1080p60。目标显示器最高刷新率改为 144 Hz 时，帧率目标相应为平衡与节能均为 144 FPS，并继续受源帧率限制。不同显示器使用不同素材时，各自按对应显示器需求处理。各显示器始终有自己的实际尺寸输出表面，显示时独立缩放。

同一适配器上的相同媒体同步播放时共享一次解码；每块屏幕拥有独立的非阻塞呈现队列，60 Hz、59.997 Hz 与高刷屏不会因为刷新率不同重复解码。不同显卡、不同文件或静态预览仍分开。实际所选文件变化后重新检查解码能力，不能沿用源编码的失败结论来禁止副本硬解。

新 Renderer 的首帧确认是切换完成的依据。UI 区分用户期望档位、生成任务状态与实际播放状态；副本尚未完成、首帧尚未到达或解码失败时，不能报告已经应用。

## 任务页面与进度

“系统设置”选择播放档位；“存储与节能优化”管理源文件、已完成副本及生成任务。源文件不是“原画副本”。

任务状态包括排队、等待接通电源、生成中、已暂停、完成和失败。生成进度来自 FFmpeg 处理时间与源时长，不按耗时猜百分比。切换编码候选时重新计量，完整文件通过验收前不提前宣布完成。预计剩余时间是估计值，会随路线与处理速度变化。

后台任务请求与进度原子持久化；写入前后核对取消、暂停及替代请求。写盘采用百分比变化和时间节流，取消或失败的旧任务不能重新写出“仍在生成”的状态。

同一档位存在多个完整规格时，页面和容量统计不得把它们误当成不存在；删除操作仍受播放租约和最后可播放文件规则约束。

## 验证范围与尚未完成的工作

`scripts/test-video-pipeline.ps1` 提供真实短视频回归：生成 10-bit SDR、PQ、HLG v210 MOV 及带 90° DisplayMatrix 的旋转 MOV，调用真实转码器，检查目标编码/色彩标签、尺寸、帧率、时长、完整解码和源 SHA-256 不变。亮度统计只排除近乎全黑/全白，不能代替色调映射的视觉认证。

还需要按 [视频运行环境](VIDEO_ENVIRONMENT.md) 的矩阵验证不同代际和厂商实机：长时运行、4K 高帧率输入、未知色彩、坏文件、多显卡、不同刷新率双屏、循环、屏保/锁屏往返、电池切换、取消和退出。单机自动化通过不等于 NVIDIA、Intel、AMD 全部驱动已认证。

跨进程断点续编码、纯 GPU 缩放/色彩全链路、完整硬件/驱动认证矩阵属于后续工作。
