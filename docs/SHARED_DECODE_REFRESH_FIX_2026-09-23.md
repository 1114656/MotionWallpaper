# 共享解码与平衡帧率修复

日期：2026-09-23。

## 本机问题与修改

修复前，GTX 1070 的两个 Renderer 同时解码同一个 3840×2160 / 90 FPS H.264 副本。采样的视频解码占用分别约 43% 和 41%，合计约 84%。两块显示器在 Windows 整数设置中都是 60 Hz，物理信号实际为 60/1 与 59997/1000。原来的精确刷新率分组把它们拆成了两条解码链。

现在按实际播放文件、显示适配器及静态预览状态分组，不再按刷新率拆分同步解码。每屏保留独立的 waitable swap chain、最大帧延迟 1 和 `Present1(..., DXGI_PRESENT_DO_NOT_WAIT, ...)`；未就绪的输出不会等待后再阻塞其他输出。组内保存每屏的精确刷新率用于路由身份，任何输出时序改变或热插拔仍会重建对应路由。不同显卡、不同文件、未知显示适配器以及静态预览仍保留安全隔离。

平衡档不再给刷新率增加 30 FPS，尺寸规则不变。副本继续使用现有整数刷新率预算，这台机器的两个输出共同选择 4K60；较低帧率源保留其原始有理数帧率。相同比例且共用源文件的不同规格显示器采用组内最大尺寸和刷新预算，不为较低刷新率的屏幕重复解码。不同裁切比例使用不同实际副本时仍是不同解码文件。

缓存文件名已经包含目标帧率：60 Hz 会请求 `balanced-60-...-v7.mp4`，不会将旧的 `balanced-90-...-v7.mp4` 当作新规格使用。现有输出校验同时检查实际视频帧率，90 FPS 文件无法通过 60 FPS 验证。原画模式、节能尺寸规则、低帧率源与原文件保留策略不变。

实机验证还发现：交换链等待时，Media Engine 可以反复返回同一个可用帧。Renderer 现在仅在时间戳改变或第一次获得帧时增加解码序号，避免重复上传同一画面、虚增播放进度。循环回到较小时间戳仍计作新帧。

## 验证

- `scripts/build-native.ps1`：115 项测试全部通过，零警告、零错误。
- 路由回归覆盖 60/59.997、60/59.94、60/144 Hz 共用解码，各屏时序保留、较慢输出时序变更、不同适配器/素材/静态预览隔离，以及热插拔身份。
- 真实 Renderer 测试使用两块不同的实际显示器；保留单屏机器上的双输出回退。覆盖首帧、持续进度、冻结和恢复，并限制重复帧造成的计数膨胀。
